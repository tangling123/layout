# EDA 版图工具（GDS / OASIS）架构设计

> 状态：**v0.2 / 设计阶段**——本文档只描述框架与模块逻辑，**不包含实现代码**。
> 目标平台：**macOS（Apple Silicon）+ Linux x86_64**；不交付 Windows（见 01 §7）。
> 技术栈：C++20 + Qt 6.7（Widgets + OpenGL）+ CMake ≥ 3.21 + zlib（+ 选定几何库，见 09）。
> 界面语言：**英文**（不做多语言/i18n，见 01 §6）。
> 文档语言：中文（设计与评审用）；产品界面英文。
> 对标工具：**KLayout**（功能对齐矩阵见 [docs/10](docs/10-KLayout功能对齐矩阵.md)）。

---

## 1. 产品定位

一个**以查看为主、可逐步扩展到编辑**的版图（layout）工具，能力向 **KLayout** 看齐，
但按「先看、再改、后分析」的顺序生长：

| 能力 | V1 查看 | V2 编辑（可替代日常改版） | V3 对齐/分析 |
|---|---|---|---|
| 打开 GDSII（.gds/.gds2/.gdsii） | ✅ | ✅ | ✅ |
| 打开 OASIS（.oas） | ✅（含 CBLOCK/表格/REPETITION） | ✅ | ✅ |
| 缩放 / 平移 / 适配窗口 / 缩放到光标 / 鼠标位置缩放 | ✅ | ✅ | ✅ |
| 层次展开（SREF/AREF）、Cell/Instance 树、指定 cell 为顶层 | ✅ | ✅ | ✅ |
| 图层树 / 显隐 / 配色 / 顺序 / 填充与图案 / `.lyp` 读写 | ✅ | ✅ | ✅ |
| 选择与属性面板 / 同层同形高亮 / 定位到图元 | ✅ | ✅（可改属性） | ✅ |
| 标尺 / 测量 / 吸附（网格、顶点、边、中心） | ✅ | ✅ | ✅ |
| 网格、坐标与缩放状态、书签、快捷键 | ✅ | ✅ | ✅ |
| 导出 PNG / SVG、命令行截图 | ✅ | ✅ | ✅ |
| **保存 / 另存为**（GDS/OASIS 重写；**默认原地覆盖** + `.bak` + 冲突检测） | ❌ | ✅ | ✅ |
| **编辑**：绘制（box/polygon/path/text）、删除、移动、复制、旋转/镜像 | ❌ | ✅ | ✅ |
| 顶点编辑、路径宽度、实例摆放与阵列、修改实例所指 cell | ❌ | ✅ | ✅ |
| **撤销 / 重做（事务）**、编辑历史面板、脏标记与保存提示 | ❌ | ✅ | ✅ |
| 图层级操作（改层号、批量迁移、克隆到新层） | ❌ | ✅ | ✅ |
| 布尔运算（merge / and / or / xor / size）、打散、转多边形 | ❌ | ✅ | ✅ |
| 编辑检查（自交、零宽、越界、重叠） | ❌ | ✅ | ✅ |
| DRC 结果浏览（RDB / XML / ASCII 标记） | ❌ | 插件 | ✅（插件） |
| 脚本宏（Python 为主） | ❌ | ❌ | ✅（插件） |
| DRC / LVS 引擎、PCell 引擎、网表提取 | ❌（长期不做，见 §6） | ❌ | ❌ |

**性能目标（硬指标，用于驱动设计）**

- 1 GB GDS、约 10⁷ 图元：打开 ≤ 15 s（有进度、可取消），内存 ≤ 4 GB。
- 平移/缩放 ≥ 30 FPS（Retina、16″ 视口），单帧 CPU 构建预算 ≤ 8 ms。
- 首次「适配窗口」显示 ≤ 2 s（先显示包围盒/LOD，再逐层细化）。
- 任意时刻 UI 主线程单次阻塞 ≤ 50 ms（不允许同步解析大文件）。
- 编辑：拖动/绘制预览 ≥ 60 FPS（只画叠加层，不重建几何）；松手提交到画面更新 ≤ 100 ms
  （被改 cell ≤ 2×10⁵ 图元时）；撤销/重做单步 ≤ 50 ms。
- **规模假设**（据此取舍复杂度）：单文件 ≤ 1 GB、图元 ≤ 2×10⁷、层次深度 ≤ 64、
  单 cell 图元 ≤ 10⁶、AREF 展开实例 ≤ 10⁵。因此**不做**分块流式 LOD、百万实例折叠等极端优化，
  只保留接口（05 §6）；超出假设时降级为「提示 + 部分显示」，不保证流畅。

## 2. 技术选型

| 关注点 | 选择 | 理由 | 备选（未采用） |
|---|---|---|---|
| UI 框架 | **Qt 6 Widgets** | 桌面工具需要 dock、菜单、表格、树；成熟稳定 | QML（表格/多窗口麻烦） |
| 渲染 | **QOpenGLWidget（GL 4.1 Core）+ 抽象 `IRenderer`** | 顶点批处理 + 实例化，性能足够；成本低于自研 RHI | QRhiWidget/Metal（V2 迁移目标） |
| 验证用后端 | **CPU 软件渲染器（QPainter）** | 先保证模型/坐标/层次正确，再上 GPU；亦用于导出 | 直接上 GL（调试成本高） |
| 坐标系 | **整数 DBU（int32 存储 / int64 运算）+ 渲染前转 double µm** | 避免浮点累计误差，与 GDS 语义一致 | 全 double（大坐标丢精度） |
| 并发 | **QThreadPool + QtConcurrent** | 与 Qt 事件循环自然集成，自带进度/取消套路 | std::thread 池 |
| 解析器 | **手写流式解析器** | 完全掌控错误定位、懒加载、性能 | gdstk / libGDSII（OASIS 支持弱） |
| 压缩 | **zlib（系统库）** | OASIS CBLOCK 只需 deflate | libdeflate（优化项） |
| 构建 | **CMake + Presets** | IDE 无关，Qt 6 官方推荐 | qmake |
| 测试 | **Qt Test（单元）+ 黄金图像对比** | 与 Qt 生态一致；渲染可回归 | Catch2 |
| 日志 | **QLoggingCategory** | 零额外依赖，按模块开关 | spdlog |
| 配置 | **QSettings + `.lyp`（图层属性）+ `.eda.json`（视图状态）** | 用户默认值 + 文件级样式 | 自研配置系统 |
| 界面语言 | **英文硬编码文案**（保留 `tr()` 但不做翻译文件） | 用户明确不需要中文；省掉 i18n 流程与文案维护 | Qt Linguist 多语言 |
| 目标平台 | **macOS 13+（arm64，兼顾 x86_64）+ Linux x86_64（glibc ≥ 2.31，GL 4.1+）** | 用户实际交付环境；只维护 clang/gcc 两套工具链，省掉 MSVC/Win 分支 | Windows（不做） |
| 几何运算（V2） | **Clipper2（Boost 许可，整数坐标）** 或自研扫描线 | 布尔/尺寸运算的鲁棒性远比自研容易；整数坐标与 DBU 天然契合 | Boost.Geometry（浮点、重） |
| 写入器 | **自研 GDS/OASIS Writer**（与 Reader 共享类型表） | 写要能控制磁盘序、属性、表格、单位；第三方库改写会丢信息 | 只用第三方库 |

## 3. 模块地图（总览）

```
                       ┌──────────────────────────────┐
                       │  app（应用/控制器层）           │
                       │  Application, Document,       │
                       │  DocumentController,          │
                       │  EditController, EditHistory, │
                       │  TaskRunner, Settings         │
                       └───┬──────────┬───────────┬────┘
                           │          │           │
             ┌─────────────▼──┐   ┌───▼────────┐  │
             │ ui（表现层）     │   │ plugin     │  │
             │ MainWindow,    │   │（可选）      │  │
             │ LayoutView,    │   └───┬────────┘  │
             │ 各 Dock 面板    │       │           │
             └─────┬──────────┘       │           │
                   │                  │           │
        ┌──────────▼───────┐  ┌───────▼───────────▼──────┐
        │ render（渲染层）   │  │ editing（编辑层）         │
        │ Camera2D,        │  │ Transaction/ChangeSet,   │
        │ IRenderer,       │  │ EditOps, SnapEngine,     │
        │ GlRenderer,      │  │ EditCheck, BooleanOps(V2)│
        │ SwRenderer, ...  │  └───────────┬──────────────┘
        └──────────┬───────┘              │
                   │                      │
        ┌──────────▼───────┐              │
        │ scene（场景层）    │              │
        │ SceneGraph,      │              │
        │ CellGeometry,    │              │
        │ SceneBuilder,    │              │
        │ LodPolicy, ...   │              │
        └──────────┬───────┘              │
                   │                      │
        ┌──────────▼──────────────────────▼──────┐
        │ io（格式层）                            │
        │ FormatRegistry, GDS/OASIS Reader+Writer,│
        │ StreamReader, RealDecoder, LayerMap     │
        └──────────────────┬──────────────────────┘
                           │
        ┌──────────────────▼──────────────────────┐
        │ core（内核层，无 Qt 依赖）                 │
        │ Geometry, Transform, Units,             │
        │ Layout(mutable)/Cell/Shape/Instance,    │
        │ Transaction/ChangeSet, LayerKey, Result │
        └─────────────────────────────────────────┘
```

**依赖方向严格单向：上层依赖下层，下层不得反向依赖。**
`core` 不 include 任何 Qt 头文件（可无 GUI 单测，可被 CLI 工具复用）。
`editing` 只依赖 `core`/`io`，**不经过 `scene`**：编辑改的是 `Layout`，由 `scene` 事后增量重建几何。

**命令层（见 [docs/11](docs/11-命令总线与命令协议.md)）**：`ui` 不直接调 `DocumentController`/`EditController`，
而是 `ui → app::CommandRouter → command::CommandBus → editing`。
`command` 无 Qt、只依赖 core+editing，是**唯一写入/视图变更入口**：
菜单、快捷键、工具栏、面板、视口工具、内置控制台、插件、外部脚本全部走同一条路径。

## 4. 关键架构决策（ADR 摘要）

| 编号 | 决策 | 理由 / 影响 |
|---|---|---|
| D1 | 分层 core / io / scene / render / editing / ui / app / plugin，依赖单向 | 解析器可独立测试；渲染后端可替换；UI 不碰数据模型 |
| D2 | 渲染抽象为 `IRenderer`，先实现软件后端再实现 GL 后端 | 软件后端验证坐标/层次/图层正确性；GL 只负责"画得快" |
| D3 | 坐标用整数 DBU（int32 存储，int64 中间运算），只在相机层转 double µm | 与 GDS 语义一致；避免 AREF 累加浮点误差 |
| D4 | 文档对外暴露**不可变渲染快照** `shared_ptr<const SceneGraph>` | 构建线程写、渲染线程读，无锁；切换快照 = 原子指针交换。**编辑后只重建脏 cell 的 `CellGeometry`，其余条目按 `shared_ptr` 复用** |
| D5 | 场景保留**层次树**（不预先全量拍平），按节点屏幕尺寸递归 LOD | 1e5 个 AREF 实例 × 1e3 图元全拍平会爆内存；层次树可剪枝 |
| D6 | 每个 cell 几何做 CPU 归一化 + **GPU 缓存（LRU）** | 同一 cell 被引用上万次也只上传一次顶点 |
| D7 | 格式解析通过 `FormatRegistry` + `FormatReader/Writer` 统一 | 后续加 DXF/LEF/CIF 不改上层；OASIS 可独立开发 |
| D8 | 大文件渐进策略：先全量顺序加载；预留「两遍扫描 + 懒加载 cell」 | GDS 是顺序流；OASIS 尾部有 offset table，天然可随机访问 |
| D9 | 耗时操作统一走 `TaskRunner`（进度 + 取消 + 结果回投主线程） | UI 不卡；解析/构建/保存/导出同一套路 |
| D10 | 选择用「cell + 元素稳定句柄」标识，不用裸指针或下标 | 元素插入/删除后仍可定位；撤销、书签、插件引用都依赖它 |
| D11 | `core::Layout` **可变**，所有修改经 `Transaction` 记录前像（before-image） | 撤销/重做、脏 cell 追踪、批量编辑的原子性都由同一机制提供 |
| D12 | 元素句柄 = `(CellId, ElementKey)`，`ElementKey` 为**带 generation 的 slot 索引** | 删除后旧句柄自动失效（不会误改新元素）；O(1) 访问 |
| D13 | 编辑提交后**增量发布**：只重建被改 cell 的 `CellGeometry`，并沿父链更新包围盒 | 一次拖动能控制在毫秒级；避免全场景重建 |
| D14 | 交互期间的图形用**叠加层预览**（ghost），松手才提交事务 | 拖动 60 FPS 不需要重建几何；渲染/数据彻底解耦 |
| D15 | 编辑能力按「查看 → 基础编辑 → 布尔/检查」三级推进，接口先留好 | 编辑会长期演进，先把事务/句柄/写入器这些不可逆的地基钉死 |
| D16 | 界面操作统一为**命令**：`ui → CommandRouter → CommandBus → editing`，命令无 Qt、可文本化 | 菜单/快捷键/面板/工具/控制台/脚本/插件同一条路径；顺带解决插件 ABI、宏录制与自动化（11） |

## 6. 明确不做（长期范围外）

- **DRC / LVS 引擎、网表提取、器件识别**：KLayout 的 DRC 是脚本化引擎（Ruby），
  工作量独立成项目；本工具只做「结果查看」。
- **PCell / 参数化单元引擎**：不做参数求值器；读入时按已求值的静态图形处理。
- **OPC / 掩模数据准备流程**、3D 工艺剖面、多用户协同、云端渲染。
- **自研文件格式**：只做标准格式（GDSII / OASIS）及少量导入格式的读写。
- 不做 `NODE`/`BOX` 之外的非几何记录的语义解释（只原样保留以便回写）。

## 7. 已确认的方向（v0.4）

| 问题 | 结论 | 对设计的影响 |
|---|---|---|
| 主要用途 | 查看为主，后续扩展到**能替代日常改版**的编辑 | `Layout` 可变；事务/撤销/写入器从 V2 起是一等公民（09） |
| 编辑强度 | 不是「挪几根线」：绘制、改属性、层次编辑、布尔运算、打散都要有 | 布尔运算与编辑检查从 V3 **前移到 V2（E3）**；Clipper2 成为 V2 依赖 |
| 保存 | **支持原地覆盖保存**，且是 `Cmd+S` 的默认行为 | 原子写（tmp → fsync → rename）+ `.bak` + 外部修改检测 + 残留临时文件恢复（09 §7） |
| 图层属性 | 复用工艺厂 **`.lyp`**（KLayout 兼容），V1 即读+写 | `.lyp` 是图层属性的权威格式；`.eda.json` 只存视图状态（01 §6、08 §2） |
| 规模 | 无百万级 AREF，常规文件/层次规模 | 不做分块流式 LOD 与百万实例折叠，只留接口（05 §6） |
| 界面语言 | 英文，不做中文 | 不引入 `.ts`/翻译流程；文案写英文常量，保留 `tr()` 仅作口子 |
| 对标程度 | 向 KLayout 看齐 | 功能矩阵（10）分级推进；交互习惯按 10 §13 实测表对齐 |
| 平台 | macOS（Apple Silicon）+ Linux x86_64，**不交付 Windows** | 只维护 clang/gcc 工具链；打包 dmg + AppImage/deb（06 §6） |
| 修改入口 | **UI 只发命令**，底层只有一个写入口 | `ui → CommandRouter → CommandBus → editing`；命令可文本化，控制台/脚本/socket/插件共用（11） |

**仍待确认（不阻塞 M0）**

1. 是否有可用的**真实版图样例**（用于性能基线与 KLayout 截图对齐）。若涉密，用 gdstk 生成的
   合成样例代替，验收标准不变。
2. 交付形式：Linux 只要 AppImage，还是同时要 deb/源码构建说明？
